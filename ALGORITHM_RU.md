# Алгоритм сериализации и десериализации

Документ описывает алгоритм, реализованный в `codec`: как значения Go
обходятся, преобразуются в граф узлов и бинарный поток, а затем
восстанавливаются, включая циклы, общие ссылки и срезы с общим backing array.
Это описание реализации формата версии 1, а не обещание совместимости любых
двух версий программы. Детали бинарного представления приведены также в
[FORMAT.md](./FORMAT.md).

## 1. Основная идея

Сериализатор не пишет объект в поток непосредственно во время рекурсивного
обхода исходного значения. Сначала он строит внутреннее представление
достижимого графа:

```text
значение Go -> узлы и связи -> перенумерованный граф -> бинарный поток
```

Этот предварительный проход нужен, чтобы обнаружить одинаковые адреса,
циклические ссылки, указатели на уже встреченные значения и срезы, которые
перекрывают одну и ту же backing array. После обхода значения узлов записываются
в порядке графа. Простые ссылки, forward references и связи указателей могут
указывать на узел, который будет полностью восстановлен позднее.

Десериализатор действует в обратном направлении не в один шаг:

```text
бинарный поток -> значения и временные контейнеры -> восстановление связей
```

Сначала создаются значения и запоминаются незавершенные связи; затем отдельные
фазы восстанавливают slice expressions, указатели, ссылки и элементы карт.

## 2. Участники и состояние

`Serializer` хранит значения графа в `values` и несколько индексов:

- `childs` задает дочерние узлы и используется для обхода и записи;
- `parents` связывает узел с его родительским контейнером;
- `addresses` обнаруживает повторно встреченные адресуемые значения;
- `ptrValues` и `ptrs` связывают значения-цели с указателями на них;
- `refs` хранит найденные повторные ссылки;
- `slices` (`reflex.SliceMap`) группирует совместимые строки, массивы и срезы
  по общей памяти;
- `imap` сопоставляет внутренние идентификаторы графа с идентификаторами,
  используемыми в потоке.

Идентификаторы графа, появившиеся во время обхода, не следует считать
идентификаторами бинарного потока. Перед записью выполняется обход дерева
`childs`, заполняющий `imap`; все сериализуемые ссылки и указатели используют
эту нумерацию.

`Unserializer` хранит исходный поток и позицию чтения, массив восстановленных
значений `values`, а также таблицы ожидающих действий:

- `slices` — выражения среза, которые надо применить к родительскому значению;
- `refs` — места, ожидающие значение по идентификатору узла;
- `maps` — пары ключ/значение карт, вставляемые после восстановления ссылок.

## 3. Подготовка графа при сериализации

### 3.1. Обход значений

`Encode` запускает обход корневого значения через `visit`. Для каждого значения
создается узел. Дальнейшее поведение зависит от `reflect.Kind`:

- структуры обходятся по полям;
- массивы и срезы обходятся по элементам;
- карты обходятся по ключам и значениям через `MapRange`;
- интерфейсы раскрываются до динамического значения;
- ненулевые указатели связываются с узлом значения, на которое они указывают;
- строки регистрируются в `SliceMap`, чтобы обнаружить общую память;
- примитивы остаются конечными узлами.

Для обычной структуры дочерние поля добавляются в порядке объявления. Если
реестр обнаруживает у типа теги `codec`, обход добавляет только поля с такими
тегами, не помеченные `deprecated`. Значение поля представлено контейнерным
узлом и отдельным дочерним узлом значения: это позволяет явно представить
адресуемость полей и поддержать указатели на них.

Интерфейс сохраняет динамический тип: его дочернее значение будет записано как
полный узел со своим type ID. Само статическое объявление интерфейса не
определяет тип содержащегося значения.

### 3.2. Учет ссылок и циклов

Для ссылочных значений сериализатор использует адреса вместе с типами, чтобы
не смешивать разные значения, случайно имеющие одинаковый числовой адрес.
При повторной встрече известного значения запись его содержимого второй раз
не требуется: в графе фиксируется ссылка на уже зарегистрированный узел.

Указатели обрабатываются отдельно от обычных ссылок. Для ненулевого указателя
сериализатор регистрирует адрес и тип целевого значения. Если цель уже
обнаружена, указатель связывается с ней; иначе значение-цель добавляется как
узел, доступный для записи на верхнем уровне графа. Такая схема разрывает
рекурсию при циклах, например `node.Next = node`, не теряя саму связь.

В потоке ссылки кодируются как `meta_ref` и ID узла. Идентификатор может
указывать как на уже прочитанный узел, так и вперед. Поэтому при чтении
десериализатор либо сразу назначает известное значение, либо записывает
ожидающее присваивание для заключительной фазы.

Итерация по карте имеет порядок, определяемый Go и не гарантирует стабильный
порядок между сериализациями. Это не меняет семантику восстановленной карты,
но байтовое представление карты может различаться.

### 3.3. Объединение срезов

`SliceMap` описывает диапазоны памяти зарегистрированных строк, массивов и
срезов одного типа элемента. Для диапазонов с ненулевым размером элемента он
определяет отношения «тот же диапазон», «родитель», «дочерний» и «частично
перекрывающийся». Если диапазоны перекрываются, но ни один не содержит другой,
создается виртуальный общий родитель, охватывающий нужные длину и capacity.

После основного обхода `visitSlices`:

1. посещает виртуальных родителей, чтобы их данные также оказались в графе;
2. переносит дочерние значения элементов в узлы общего родителя;
3. заменяет отдельные представления вложенных срезов ссылками/выражениями на
   родительский узел, где это соответствует общей памяти.

При записи отдельный slice expression содержит ID родителя, начальный и
конечный индексы и, для среза, верхнюю границу `max`. Десериализатор применяет
его позднее, чтобы восстановить не только данные, но и отношение общей backing
array.

Для элементов нулевого размера SliceMap не выводит общность backing storage из
адресов: Go может использовать один адрес для множества таких элементов.
Длина и capacity при этом сохраняются в представлении среза. Срезы/строки с
разными типами элементов, созданные, например, через `unsafe.Pointer`, не
объединяются в общий родитель.

### 3.4. Перенумерация узлов

После обработки срезов `renumberGraph` выполняет обход дочерних узлов от
виртуального корня и присваивает последовательные ID. Именно эта нумерация
используется в байтовом потоке для обычных ссылок, slice expressions и
указательных записей. Узлы, необходимые из-за указателей или виртуальных
родителей, записываются как корневые узлы графа.

## 4. Запись бинарного потока

Начало потока имеет вид:

```text
version encoded_nodes [pointer_links]
```

Первый байт — версия формата (`1`). Каждый узел начинается с `u3` type ID,
после которого идет payload значения. `uN` обозначает целое с префиксом
длины в `N` битах; числа занимают минимальное количество байт. Для знаковых
значений применяется преобразование `i2u`, затем результат кодируется как
unsigned. Многобайтовая полезная часть записывается в big-endian.

### 4.1. Узлы и идентификаторы типов

Обычный узел:

```text
u3(type_id) value_payload
```

Type ID разрешается через `TypeRegistry`; сам поток не содержит описания Go
типа. Порядок обхода `childs` задает порядок вложенных payload. Для значений,
которые являются прямыми полями, элементами массива/среза или элементами карты,
тип берется из объявленного контейнера. Для корневых узлов и динамических
значений интерфейса записывается type ID.

### 4.2. Примитивы и специальные значения

- `nil`, `false` и `true` имеют отдельные маркеры.
- `uint8`/`int8` записываются одним байтом; другие целые используют компактные
  `u2`/`u3`/`u4` в зависимости от ширины типа.
- `int`, `uint`, `uintptr` используют кодирование ширины 64 бита; `uintptr`
  сохраняет числовое значение, но не делает адрес переносимым.
- `float32` и `float64` кодируют IEEE-754 представление; `complex` содержит
  последовательно real- и imaginary-части.
- Строка без общей backing storage записывается как signed-длина и байты.
  Строка, представленная как выражение над общим родителем, ссылается на
  родительский узел и индексы.
- `nil` map/slice/pointer/function/channel отличаются от ненулевых пустых
  значений. Для среза отдельно записываются длина и capacity.
- Для канала сохраняются nilness, направление типа и capacity; содержимое
  канала не сериализуется.
- Ненулевая функция представляется зарегистрированным function ID, а не
  машинным кодом или замыканием.
- `unsafe.Pointer` записывается как числовой адрес и не восстанавливается как
  безопасный переносимый указатель.

Точные маркеры и раскладка payload описаны в [FORMAT.md](./FORMAT.md).

### 4.3. Составные значения

- **Массив:** элементы записываются по индексу; отдельного заголовка массива
  нет.
- **Срез:** маркер, длина, capacity и значения элементов. Нулевой capacity
  кодируется без обхода backing storage.
- **Срез-выражение:** маркер slice expression, ID родителя и индексы
  `start/end/max`; фактическое значение присваивается при восстановлении.
- **Карта:** nil-маркер либо non-nil, количество пар и последовательность
  ключ/значение. Относительный порядок пар не гарантирован.
- **Структура без тегов:** маркер структуры и значения полей в порядке
  объявления.
- **Интерфейс:** полный динамический узел, включая динамический type ID.
- **Указатель:** nil/non-nil маркер в основном потоке; связь между значением
  и указателем дописывается отдельно.

Повторный объект может быть закодирован как `meta_ref` вместо повторного
payload. Таким образом, наличие вложенного значения не всегда означает
рекурсивную запись его содержимого.

### 4.4. Теги структур

Если для типа структура зарегистрированы `codec`-теги, запись переключается
в tagged-режим. Поле должно иметь уникальный неотрицательный `id`; дублирование
ID приводит к ошибке разбора тегов при регистрации типа. Поток содержит число
сериализуемых tagged-полей, затем пары `field_id, field_value`.

В tagged-режиме сериализатор включает только поля с тегом и без `deprecated`.
Нетегированные поля не записываются. Десериализатор ищет поле по ID в
метаданных реестра; отсутствующие в потоке поля сохраняют нулевое значение.
Тегированное deprecated-поле присутствует в метаданных и может быть прочитано
из старого потока, но не записывается новым сериализатором. Неизвестный ID
поля вызывает ошибку декодирования.

Без активных тегов структура кодируется позиционно. Поэтому изменение порядка
или состава ее полей несовместимо с уже записанными позиционными данными.

### 4.5. Сериализуемые пользователем типы

Если тип реализует `Serializable`, обычный обход его внутренней структуры
заменяется вызовом `Serialize()`. Результирующий byte slice записывается с
маркером non-nil и длиной. Декодер передает payload в `Unserialize([]byte)`,
проверяет ошибку/отсутствие результата и устанавливает возвращенное значение,
если его тип преобразуем к ожидаемому.

Такой payload является непрозрачным для графового алгоритма: ссылки внутри
пользовательского byte slice автоматически не обнаруживаются и не восстанавливаются.
Сам пользовательский формат должен включать все необходимые данные и проверять
вход.

### 4.6. Связи указателей

После основных узлов сериализатор дописывает записи вида:

```text
meta_ref target_id pointer_id [pointer_id ...]
```

Первый ID указывает на значение-цель, последующие — на значения-указатели,
которые должны на нее ссылаться. Такой хвост отделен от основного потока
маркерами `meta_ref` и содержит только компактные ID. За счет отложенной записи
поддерживаются циклы и указатели на поля/элементы, даже если соответствующие
узлы были обнаружены в другом месте графа.

## 5. Десериализация

### 5.1. Чтение основного потока

`Decode` сначала проверяет, что вход не пуст, сбрасывает состояние предыдущего
вызова и проверяет байт версии. Далее декодер читает узлы, пока следующий байт
не является маркером `meta_ref`; на этой границе начинаются записи связей
указателей.

Для каждого узла декодер:

1. читает type ID и разрешает его через `TypeRegistry`;
2. создает нулевое значение соответствующего типа;
3. добавляет значение/контейнерные слоты в `values`, согласованные с
   идентификаторами потока;
4. читает payload согласно типу;
5. сохраняет ссылки вперед и slice expressions в таблицах отложенных действий.

Срезы выделяются через `reflect.MakeSlice` с исходными длиной и capacity;
структуры, массивы и интерфейсы заполняются рекурсивно. Интерфейс декодирует
свой динамический узел и помещает получившееся значение в интерфейс.

Чтение использует reflection и компактные integer helpers. Неполные или
некорректные данные могут вызвать panic внутри декодирующего кода; `Decode`
перехватывает его и возвращает как `error`. Это не означает полной проверки
безопасности произвольного недоверенного потока: лимиты размера/ресурсов должны
рассматриваться отдельно.

### 5.2. Отложенные ссылки в картах

При декодировании карта заранее создается с ожидаемым количеством элементов.
Если типы ключа и значения не являются pointer/interface, пара сразу вставляется
через `SetMapIndex`. Если хотя бы одна сторона — pointer или interface, ID
ключа и значения сохраняются в `maps`: окончательная вставка откладывается до
восстановления связей. Это позволяет картам содержать значения, которые
ссылаются на другие узлы или являются частью циклов.

### 5.3. Фазы восстановления

После основного потока выполняются этапы в следующем порядке:

1. **Slice expressions (`restoreSlices`).** Родительские значения нарезаются
   через `Slice`/`Slice3`; строка и `[]byte` при допустимой общей byte-памяти
   связываются через unsafe-представление. Результат записывается в сохраненный
   слот назначения.
2. **Указатели (`restorePointers`).** Читаются завершающие pointer-link records;
   указатели назначаются на значения-цели.
3. **Обычные ссылки (`restoreReferences`).** Все места, ожидающие конкретный
   ID, получают итоговое значение из `values`.
4. **Карты (`restoreMaps`).** Отложенные пары ключ/значение вставляются в уже
   созданные карты.

Порядок существенен: к моменту вставки карты ссылки и указатели уже должны
указывать на восстановленные значения, а slice expressions должны быть
применены к родителям.

## 6. Реестр типов и функций

Type ID и function ID имеют смысл только в конкретном `TypeRegistry`.
Сериализатор получает ID по имени типа/функции; декодер по этому ID находит
соответствующий тип или зарегистрированное значение функции. Для обмена данными
между процессами нужно обеспечить совместимые реестры и одинаковое назначение
ID. Автоматическая регистрация удобна, но порядок первого обнаружения типов
может отличаться между путями выполнения и запусками.

Для стабильного протокола следует заранее зарегистрировать все используемые
типы/функции и передавать согласованный реестр и сериализатору, и
десериализатору. Регистрация рекурсивного типа также регистрирует типы полей и
элементов, но сама по себе не регистрирует произвольные значения функций;
для функции необходимо зарегистрировать ее значение.

## 7. Повторное использование объектов кодека

`Serializer.Encode` очищает индексы после завершения записи. Буфер `values`
обнуляется и сохраняет capacity, поэтому повторные вызовы могут переиспользовать
его backing storage, не удерживая ссылки на ранее сериализованные объекты.
Другие внутренние индексы также очищаются для следующего графа. Экземпляры
`Serializer` и `Unserializer` содержат изменяемое состояние; одновременные
вызовы на одном экземпляре не следует считать потокобезопасными.

`Unserializer.Decode` очищает таблицы временных связей и заново устанавливает
текущий входной поток перед чтением следующего значения.

## 8. Ограничения и важные свойства

- Формат версионирован, но не самодостаточен: для type/function ID нужен
  совместимый реестр.
- Ненулевой канал восстанавливается как новый пустой канал той же capacity и
  направления; переданные через него значения не сохраняются.
- Функция восстанавливается только если ее значение зарегистрировано; состояние
  замыкания этим механизмом не сериализуется.
- Числовые значения `uintptr` и `unsafe.Pointer` нельзя считать переносимыми
  или безопасно восстановленными адресами.
- Общая память строк/срезов разных типов элементов, например
  `[]uint32` и `[]byte`, созданных через `unsafe.Pointer`, не представляется
  общей backing array.
- Непрозрачный `Serializable` payload не участвует в обнаружении ссылок
  внутреннего графа.
- Позиционная сериализация структур чувствительна к порядку полей. Tagged-режим
  уменьшает эту зависимость для полей с ID, но требует уникальных ID и
  согласованных тегов в реестрах обеих сторон.
- Порядок обхода map не фиксирован, поэтому для логически одинаковых
  map не гарантируется одинаковое бинарное представление.
- Десериализация отражает конкретные типы и может выделять память согласно
  длинам/capacity из потока; данные от недоверенного источника требуют
  внешнего контроля размера и происхождения.
